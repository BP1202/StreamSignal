# AGENTS.md

# StreamSignal — Agent Operating Contract

This file is the primary operating contract for any AI coding agent working inside the StreamSignal repository.

The agent MUST read and follow this file before modifying the repository.

If another instruction conflicts with this file, the agent must stop and identify the conflict instead of silently choosing an interpretation.

---

# 1. PROJECT IDENTITY

## Project

StreamSignal

## Core purpose

StreamSignal turns a citizen's uncertain urban freshwater observation into a transparent, reviewable, provenance-rich, standards-ready One Health evidence case.

The project is developed for urban freshwater surveillance and One Health evidence interoperability.

## Core product principle

StreamSignal is NOT an:

* AI pollution detector
* disease diagnosis system
* generic chatbot
* generic environmental dashboard
* generic FHIR converter
* black-box image classifier
* system that declares environmental causation from limited evidence

StreamSignal is an evidence system.

The product separates:

1. Citizen Evidence
2. Machine Assistance
3. Contextual Evidence
4. Human Decision

The system must clearly distinguish observed facts from machine-generated assistance and human conclusions.

# 3. ONE HEALTH PRINCIPLE

One Health recognizes that:

Human health
+
Animal health
+
Environmental health

are interconnected.

StreamSignal must not convert an environmental observation directly into a medical claim.

For example:

INVALID:

"This water is toxic."

"This pollution will make people sick."

"This image proves an algae bloom."

VALID:

"Citizen reported green surface material."

"Image contains visual characteristics that may warrant review."

"Similar historical observations were found."

"Human expert review is required."

Machine assistance must never be presented as confirmed scientific fact unless supported by appropriate evidence and explicitly confirmed by an authorized human workflow.

# 7. IMPLEMENTATION PLAN REQUIREMENT

Before making repository modifications, the agent MUST create an implementation plan.

The plan should contain:

## Goal

What is being built?

## Current state

What already exists?

## Implementation steps

What will change and in what order?

## Tests

How will the behavior be verified?

## Security considerations

What security risks are relevant?

## Validation

How will success be manually and automatically verified?

## Git

What commit should represent the completed task?

The agent should show the plan before editing.

Example:

```text
Implementation Plan

Goal:
Add POST /api/v1/reports.

Current state:
FastAPI foundation exists.
No Report model exists.

Files:
CREATE backend/app/models/report.py
CREATE backend/app/schemas/report.py
CREATE backend/app/api/v1/reports.py
CREATE backend/tests/test_reports.py
CREATE migration

Steps:
1. Write failing tests.
2. Create SQLAlchemy model.
3. Create Pydantic schemas.
4. Create migration.
5. Implement endpoint.
6. Run tests.
7. Test through HTTP.
8. Review security.
9. Commit.

Risks:
Validate coordinates and input length.
Do not expose internal database errors.

Validation:
pytest
API request through curl/Swagger
database persistence check
```

Only after the plan is accepted or clearly within the user's already-defined task should implementation begin.

# 14. DATABASE RULES

PostgreSQL is the primary relational database.

PostGIS is used for legitimate geospatial requirements.

pgvector is used only where vector similarity/retrieval provides a meaningful product capability.

Do NOT introduce:

* Neo4j
* a second database
* an external vector database
* a graph database

without an explicit architectural reason and discussion.

Database schema changes MUST use Alembic migrations.

Never manually modify production schema as a substitute for migrations.

Never silently drop or recreate the database during normal development.

---

# 15. MIGRATION RULES

Every schema change must have an Alembic migration.

Before creating a migration:

* inspect current models
* inspect current migration state
* understand the schema change

After creating a migration:

```text
alembic current
alembic upgrade head
pytest
```

For destructive migrations, stop and explicitly ask for confirmation if data could be lost.

Never use:

```text
DROP DATABASE
DROP TABLE
TRUNCATE
```

as a casual debugging solution.

---

# 16. API RULES

Use versioned API routes:

```text
/api/v1/...
```

API endpoints must define:

* request schema
* response schema
* validation
* appropriate HTTP status
* predictable error behavior

Do not expose:

* database passwords
* stack traces
* internal filesystem paths
* SQL queries
* secret configuration
* internal tokens

unless explicitly required for controlled development diagnostics.

---

# 17. INPUT VALIDATION

Treat all external input as untrusted.

Validate:

* strings
* lengths
* enumerations
* coordinates
* timestamps
* uploaded files
* MIME types
* file signatures
* content size

Never trust a filename extension alone.

Never trust a browser-provided MIME type alone.

Never construct SQL using string concatenation.

Use parameterized database access through SQLAlchemy.

---

# 18. FILE UPLOAD SECURITY

For citizen media:

Validate:

1. File size
2. Allowed file type
3. MIME type
4. File signature / magic bytes where applicable
5. Image decoding success
6. Safe storage name
7. Storage location

Never use the original user filename as a trusted filesystem path.

Prevent:

* path traversal
* arbitrary file execution
* oversized uploads
* unsupported executable content
* unsafe archive extraction

Metadata such as EXIF must be treated carefully because it may contain sensitive location/device information.

---

# 19. SECRETS

Never commit:

* passwords
* API keys
* access tokens
* private keys
* cloud credentials
* database credentials

Use:

```text
.env
```

for local development secrets.

`.env` must remain ignored by Git.

Provide safe examples through:

```text

```

Never print secret values in logs.

If a credential appears in source code, stop and flag it.

# 20. CORS

Development may use permissive CORS where appropriate.

Production must use explicit trusted origins.

CORS is NOT authentication.

Never describe CORS as a security boundary that prevents direct API access.

Authentication and authorization must be implemented separately when required.


# 23. LLM RULES

LLMs may be used for appropriate tasks such as:

* extracting structured information from citizen text
* generating targeted follow-up questions
* summarizing evidence
* assisting reviewers

For example:

FHIR generation should be performed through deterministic application code and validated structures.

Do not ask an LLM to freely invent an entire FHIR Bundle and assume it is valid.

The agent must not turn weak evidence into strong scientific claims.

Never infer:

```text

=
confirmed organism
```

or:

```text
environmental observation
=
human disease
```

or:

```text
similar cases
=
same cause
```

Pattern similarity is not causation.

AI assistance is not scientific confirmation.

Human review remains part of the system where scientific interpretation is required.
